Concept · Hover / Click

Spotlight

Built around two things. First: the element is cut out of every layer. The page dims, blurs and fills with light around the element's own rounded outline, and nothing is ever painted on top of it - so a dense panel of 11px copy is exactly as readable lit as it is at rest, at any beam opacity. The beam stops at the element's silhouette and carries on past it, which is also the physically honest read: a solid thing standing in a beam blocks it. Second: every instance on the page draws through one shared stage, and only one element holds the light at a time. Moving the pointer between two spotlit elements sweeps the beam across to the new one rather than lighting both at once.

Install

<script src="spotlight.js"></script>

Injects its own <style> tag defining .spotlight-el, and builds one shared set of three position: fixed layers on <body> for the whole page however many instances there are, so no companion CSS file is required - but the host element needs its own size and content, since the injected CSS sets neither.

Quick Start

<div class="spotlight-el" style="width:320px;height:230px" tabindex="0">
  <h3>Spotlight</h3>
</div>
<script src="spotlight.js"></script>

Auto-initializes against every .spotlight-el element, hover-triggered by default. tabindex="0" is optional but recommended - it makes the spotlight keyboard-triggerable via focus, not just pointer hover. To configure options: 

Spotlight.initAll('.spotlight-el', {
  angle: -25,
  color: '#bfe3ff',
});

Recipes

Move the light

angle is how far off vertical the beam rakes in, in degrees - positive leans the light in from the right, negative from the left. It is an angle rather than a fixed position because a hardcoded corner gives everything far from that corner a near-horizontal skim: the emitter is placed along the window's top edge to hit this angle from whatever it is currently lighting, so every element on the page gets the same believable rake. It's clamped into the window, so an element near one edge gets a shallower angle rather than an emitter nobody can see. 

// Light leaning in from the upper left instead
Spotlight.initAll('.spotlight-el', { angle: -22 });

// Straight down from directly overhead
Spotlight.initAll('.spotlight-el', { angle: 0 });

Blur the page as well as dimming it

darkOpacity and blurAmount are independent and stack - there's no mode to pick between. The beam is screen-blended light, so it needs something darker than the page to show up against; a blur-heavy look still wants some dim under it rather than darkOpacity: 0. 

Spotlight.initAll('.spotlight-el', {
  darkOpacity: 0.45,
  blurAmount: 16,
});

Click to spotlight

trigger: 'click' makes the element toggle on and off on click instead of tracking hover - useful for touch, or anywhere a deliberate action should hold the spotlight rather than a passing pointer. On an element also covered by a blanket initAll('.spotlight-el') call elsewhere (auto-init, say), set data-sp-trigger="click" on the element itself instead - it wins the auto-init race that a later, more specific initAll() call can't. 

Spotlight.initAll('.spotlight-el', { trigger: 'click' });

A click-latched element keeps the light: hovering something else borrows the beam, and the moment that hover ends it swings back. Worth pairing with a small lift on a short click target, though - the element is what the next click has to land on, and lift moves it up out from under the pointer by that many pixels, which on something only a couple of dozen pixels tall can put its lower edge past where the visitor is still aiming. 

Spotlight.initAll('.sp-pill', { trigger: 'click', lift: 2 });

Tight theatrical spot vs. soft overhead panel

sourceWidth is how wide the emitter is where it sits on the window's top edge, and it's the single biggest lever on the character of the light: near zero reads as a hard point-source spot with crisp edges, wide reads as a soft light panel. clearance sets how far past the element's own corners the beam's edges pass - the beam always frames the element whatever this is, since its edges are solved from the element's silhouette, so this only controls how tightly. 

// Hard theatrical spot
Spotlight.initAll('.spotlight-el', {
  sourceWidth: 6,
  clearance: 6,
});

// Soft overhead wash
Spotlight.initAll('.spotlight-el', {
  sourceWidth: 180,
  clearance: 40,
});

How far the beam carries past the element

overshoot is a multiple of the throw from the emitter to the element. 1.0 stops the beam dead at the element; the default carries it a little past, so the light that misses the element's silhouette keeps going and fades, leaving the element's own shadow in the beam behind it. 

// Beam stops at the element
Spotlight.initAll('.spotlight-el', { overshoot: 1 });

// Long throw well past it
Spotlight.initAll('.spotlight-el', { overshoot: 1.8 });

Just the light, none of the staging

dustMotes, floorGlow, edgeGlow and haloGlow each turn off one piece of the atmosphere around the beam. On a small element the full set reads as clutter rather than staging. 

Spotlight.initAll('.spotlight-el', {
  dustMotes: false,
  floorGlow: false,
  edgeGlow: false,
});

Slower or instant sweeps

sweep is how long the beam takes to swing across when the pointer moves from one spotlit element straight onto another - separate from smoothing, which is how fast the whole effect fades up and down. 0 makes the beam jump to each new element instead of travelling. 

// A long, lazy searchlight swing
Spotlight.initAll('.spotlight-el', { sweep: 650 });

// No travel at all
Spotlight.initAll('.spotlight-el', { sweep: 0 });

Externally driven (no native hover/click)

autoBind: false skips binding the element's own listeners entirely, for cases where something else already owns trigger detection for it - same reasoning as Liftoff's hoverEvents: false. Drive it with .enter() / .leave() / .toggle() instead. 

const [card] = Spotlight.initAll('.spotlight-el', { autoBind: false });
someExternalHoverSource.on('enter', () => card.enter());
someExternalHoverSource.on('leave', () => card.leave());

Notes

Why the element is cut out rather than lit: painting the beam across the element - the obvious way, and what earlier drafts of this did - means every increase in beam opacity costs the element's own content a shade of contrast, and on a light page, a screen-blended wash over a white card does nothing visible anyway except wash out the text on it. Here the beam, the scrim and the backdrop blur are all masked by the element's own rounded rect. Each cut-out is two rects rather than one: a crisp rect at the element's exact bounds, guaranteeing its interior is fully clear, and a blurred rect underneath it at the same bounds, contributing only the half of its falloff that lands outside. Growing a single blurred hole instead - the obvious fix for softness creeping inside the element - trades that artifact for a worse one: a fully undimmed ring of page hugging the element, which on a light background reads as a hard white outline drawn around it, and is bright enough to drown out the actual rim light. What makes the element read as lit is the contrast against everything around it dropping into shadow, plus a rim of light in the beam's color hugging the outside of its outline and a shadow cast away from the light - all of it strictly outside the element's own bounds.

How the beam's edges are found: not a fixed spread, but a silhouette solve. Of the element's four corners, the two at the angular extremes as seen from the emitter are picked, and the beam's edges are the rays that graze those two. That's what makes the cone land squarely around the element from any direction and at any aspect ratio - a fixed-width wedge, or one anchored to two opposite corners, slices diagonally across anything that isn't square-on to it.

One stage, not one overlay per element: all instances share a single set of layers, and the stage tracks which element holds the light. N independent full-page scrims stacking their darkness on top of each other is a whole class of bugs by itself - two elements mid-crossfade double the dim, and each extra backdrop-filter layer compounds it - and the shared stage removes the possibility rather than managing it. It also buys the sweep: the beam's aim eases toward the new element while the cut-out snaps to it immediately, so the element handed the light is legible from the first frame and the light arrives just after.

Why three separate layers on <body>: the blur panes, the scrim and the light are three position: fixed siblings rather than three children of one overlay, and that isn't tidiness. Chrome silently drops a backdrop-filter when the element is masked or clipped (issues.chromium.org/issues/40778541) and also when a sibling inside the same stacking context carries a mix-blend-mode. Put all three jobs inside one overlay div and the blur silently never renders at all. Giving the blur panes their own top-level layer with no mask, no clip and no blended sibling is what makes it work. The light layer carries mix-blend-mode: screen on the layer itself for the mirror-image reason: position: fixed always establishes a stacking context, so a blended child of a fixed overlay only ever blends against its own transparent parent - i.e. does nothing at all.

Why the blur panes are all the same size: the hole in the backdrop blur is framed by four clipping wrappers, each holding a pane that covers the whole viewport and is simply offset back into place. Sizing each pane to its own strip instead - the obvious way - leaves a visible seam along every join, because a backdrop-filter samples only what is behind its own box: four differently-sized panes blur four differently-cropped backdrops and disagree along their shared edges, drawing faint lines across the page. Identical panes sample identical backdrops and agree exactly. Their edges are rounded to whole pixels for the same reason - a fractional coordinate leaves either a hairline of unblurred page or a sliver of doubled blur along the join. It's also one uniform blur rather than a ladder of rings at decreasing radii: the rings were the first attempt at softening the sharp-to-blurred transition, and every step boundary just read as another line across the page. The single edge is hidden instead, by sitting a few px outside the element under the scrim's own falloff and the halo.

Mask regions are sized to the viewport, deliberately: an SVG <mask>'s region both clips what it masks and sizes the buffer it rasterizes into. Oversizing it to be safe is not free: at three times the viewport on each axis Chrome quietly gives up on the mask and drops the masked element entirely, leaving a scrim that is measurably present in the DOM and completely absent on screen. Nothing outside the viewport is visible anyway.

Geometry is read per frame, not polled: the stage reads getBoundingClientRect() once per frame on the one element currently holding the light, so the beam tracks scrolling, resizing and the element's own pop-scale for free - with no scroll listener, no resize listener and no safety-net polling timer. Everything downstream of that rect is guarded by a signature check, so a pointer resting on an element costs a dozen circle updates a frame for the dust motes and nothing else; the beam's two large blurred polygons and both masks are only rewritten when something actually moved.

The pop itself is driven by one continuous scalar per element (amount, 0-1) rather than a CSS class + transition, same reasoning as Liftoff: a pointer leaving mid pop-in reverses smoothly from wherever it currently sits instead of snapping or fighting an in-flight CSS transition. In hover mode, only mouse input triggers it - touch/pen pointer events are ignored. Respects prefers-reduced-motion by skipping auto-init entirely (an explicit Spotlight.initAll() call still works if you want it anyway).

Combining with Liftoff: both effects scale the host element itself through their own transform CSS rule. Applying both liftoff-card and spotlight-el to one element leaves only one transform in effect - whichever the cascade picks, not a blend of both - since two separate class rules targeting the same CSS property on the same element don't merge. A two-class selector composing both formulas into a single rule outranks either one on specificity alone, regardless of which stylesheet loaded last, and resolves it cleanly: .liftoff-card.spotlight-el { transform: translate(var(--lift-x), calc(var(--lift-y) + var(--sp-lift))) rotate(var(--lift-r)) scale(calc(var(--lift-s) * var(--sp-scale))); }. Nothing here adds that automatically - it's a one-rule fix to add wherever the two are actually combined. Picking one outright is the other valid answer, and the one this site's own homepage takes: its Spotlight card keeps .liftoff-card for the structural chrome but opts out of the effect with data-liftoff="off", so the same two-class selector states Spotlight's transform alone.

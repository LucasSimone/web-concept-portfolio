Aperture

A ring of camera-iris blades — curved panels seamed with lines, like a real diaphragm — spirals inward from the edge of the screen to the center when a link is clicked, their curved tips sealing shut at a point, then spirals back outward from that point once the next page loads, opening to reveal it. One continuous motion, split across the navigation boundary — the same shape as Shutter's rise/recede, but a twisting iris in place of a sliding panel.

Install

<script src="aperture.js"></script>

Like Shutter, this one belongs in <head>, not next to the markup it affects — as a plain, non-async/defer tag, on every page that should take part. It has to run and build its overlay before the page paints, so the initial sealed iris (when arriving from another transitioned page) shows with no flash of the page underneath. The overlay itself is a plain <div> appended straight onto <html> rather than <body> — it has to exist before <body> necessarily does, and a fixed-position element renders correctly regardless of where in the tree it sits.

Dropping the script in doesn't intercept anything by itself: navigation is off until you set selector (see Options below). With no config at all, you still get Transitions.aperture.play/cover/reveal for transitioning elements — just no link interception.

Quick Start

Turn on navigation interception by setting selector before the script runs: 

<script>
  window.TransitionConfig = {
    aperture: { selector: 'a[href]' },
  };
</script>
<script src="aperture.js"></script>

No class to add and no elements to opt in beyond that — it now listens for clicks on the whole document and intercepts any left-click on a same-origin <a href> that isn't a hash link, a download link, a target="_blank" link, or opened with a modifier key held. Clicking one spirals the iris shut, then navigates once it finishes. The reveal only plays on the page that receives that navigation — a direct load, refresh, or bookmarked visit never shows the overlay at all, and if the destination page doesn't also load aperture.js, the seal simply finishes and that page appears underneath with no reveal of its own.

Recipes

Exempt a link from the transition

Keep navigation on for the page but skip interception for one specific link, without removing the script. 

<a href="/elsewhere.html" data-no-transition>Skip the transition</a>

Override one link's blades, color, or timing

A single link can override duration, easing, panel color, line color, blade count, blade style, or spin for just its own transition, leaving every other link on the page using the default profile — this is how the demo's controls panel customizes only the Page One → Page Two link without touching the site nav around it. Whichever profile a click used — default or overridden — travels to the next page in the same handoff that triggers its reveal, so the two halves of the motion always match. 

<a href="page-two.html" data-t-duration="900" data-t-blades="5" data-t-style="curved" data-t-color="#000" data-t-line-color="#fff">
  Enter Page Two
</a>

Set the default timing, blade count, or style

Configure the page-wide profile once, alongside turning on selector: 

<script>
  window.TransitionConfig = {
    aperture: { duration: 800, color: '#eee', lineColor: '#111', blades: 6, style: 'curved', selector: 'a[href]' },
  };
</script>
<script src="aperture.js"></script>

Reconfigure after the script has already loaded

Useful for widening or changing selector from a script that runs later, rather than setting window.TransitionConfig up front. 

Transitions.aperture.configure({ selector: '[data-t-transition="aperture"]' });

Element Transitions

Beyond whole-page navigation, Aperture can also transition any element in place — seal it shut, swap what's inside, then spiral back open — with no page load involved. Mark the element class="t-el" (gives the iris a positioning context to size itself against) and call play: 

<div class="t-el" id="card">...</div>

<script>
  Transitions.aperture.play(document.getElementById('card'), {
    swap: (el) => { el.textContent = 'New content'; },
  });
</script>

play(el, options) covers el, calls options.swap(el) once it's fully sealed (waiting on it first if it returns a promise), then reveals — one call for the common case. cover(el, options) and reveal(el, options) are also public on their own, for anything that doesn't fit that cover→swap→reveal shape. All three take the same fields as the per-link data-t-* attributes above, as a plain object, and return a promise that resolves once that step finishes — they're the primitives play is built from, not a separate flow.

Blade geometry is derived from the target element's own size (rather than the viewport, as the navigation case uses), and overflow: hidden is applied to it only while animating, so it clips blade overshoot at the element's edge without ever clipping the element's normal content the rest of the time.

Every element gets independent state: two different elements (or the same element called repeatedly, e.g. to loop it) each animate on their own, with nothing shared between them. 

// Two cards, two independent seals, at the same time.
Transitions.aperture.play(cardA);
Transitions.aperture.play(cardB);

// Looping the same element.
(function loop() { Transitions.aperture.play(card).then(loop); })();

Not part of the navigation flow above — a navigating page's cover has no same-document reveal to chain into (it navigates instead), so that flow uses cover/reveal directly rather than play.

Multiple Transitions

A page can load more than one transition effect at once, each handling a different set of links. Every effect keeps its public API, its config, and its arrival flag under its own slug — window.Transitions.aperture, window.TransitionConfig.aperture, and a sessionStorage key of t-aperture-pending — so it registers alongside Shutter without either clobbering the other. This site's own layout does exactly that: both scripts load on every page, each one reacting only to links tagged with its own slug: 

<script>
  window.TransitionConfig = {
    shutter:  { selector: '[data-t-transition="shutter"]' },
    aperture: { selector: '[data-t-transition="aperture"]' },
  };
</script>
<script src="shutter.js"></script>
<script src="aperture.js"></script>

Which link uses which effect is decided by the value of data-t-transition — each script only reacts to the name matching its own slug, so a given link can only ever belong to one effect: 

<a href="/a" data-t-transition="shutter">Uses Shutter</a>
<a href="/b" data-t-transition="aperture">Uses Aperture</a>

Neither script coordinates with the other. Arriving on the next page, each one only checks whether its own sessionStorage key was set — and since only one link is ever clicked at a time, only one key is ever written, so only that one effect's reveal plays.

Running the same effect configured differently in different places is a separate case that doesn't need any of this — see the per-link data-t-duration/ -easing/-color/-line-color/ -blades/-style/-spin attributes above, which already let one script handle any number of differently configured links on one page.

That's a different multiplicity than Element Transitions' concurrent instances above — this section is about running different named effects (Shutter, Aperture, …) on one page without them colliding; that one is about running this same effect on several elements (or the same element repeatedly) at once, which works because each target keeps its own independent state rather than sharing one page-wide profile.

Methods

MethodDescription
configure(options) Merges new options into the page-wide default profile - typically called just to widen/set selector from a script that runs after aperture.js has loaded.
cover(el, options) Covers el (an element with class="t-el", or document.documentElement), resolving once fully sealed. Leaves el covered - pair with reveal().
reveal(el, options) Reveals el, resolving once fully open and cleaned up.
play(el, options) Sugar for "transition this element's content in place": covers el, runs options.swap(el) (may return a promise) once covered, then reveals. Not part of the navigation flow - that has no same-document reveal to chain into, so it uses cover/reveal directly instead.

All four are on Transitions.aperture. cover, reveal, and play take the same fields as the per-link data-t-* attributes above, as a plain options object, and return a promise that resolves once that step finishes.

Notes

Each blade is a real drawn shape, not a mask trick, and its two side edges are curves rather than straight spokes from the center — a real iris blade pivots around a point out near the rim, not the exact center, which is what makes its edges sweep tangentially as they run inward instead of radiating straight out. Two blades sharing a seam compute that shared curve from the same absolute angle so they always meet exactly, stroked in lineColor. The inner edge — filled in color — is either a true circular arc (the 'curved' style, the same shape a real iris opening traces) or a straight chord (the 'sharp' style, a more faceted, graphic opening). Their shared inner radius is driven by a single registered custom property, --t-aperture-progress, which the browser transitions natively; a requestAnimationFrame loop just samples its live computed value every frame and rebuilds all the blade paths from it, since arbitrary path geometry can't be CSS-transitioned directly. At progress 0 every blade's inner edge collapses onto the center point, giving the sealed ring its pointed tips.

Respects prefers-reduced-motion: with it set, clicking a link navigates immediately with no seal, and an arrival never plays a reveal; cover/reveal/play resolve immediately the same way — play's swap still runs, just with no seal shown around it. A back/forward (bfcache) restore also skips replaying anything — pageshow with event.persisted resets every still-active element straight to its clean, open state instead of replaying anything. Arrival state (for navigation) is tracked with a short-lived sessionStorage flag rather than anything in the URL, so it costs nothing to add and never shows up as a query param or hash.

The overlay stacks above the target element's own content, not above the whole page — for the navigation case (covering <html>) that's already the top of everything, but for an element target it's only as high as that element's own stacking context allows. A descendant with its own higher z-index can still paint above it.

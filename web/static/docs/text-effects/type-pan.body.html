Type Pan

A single line of text types itself out character by character, the caret always sitting immediately after the last revealed character so new characters reveal to its right exactly like a real typewriter. Once the typed line grows wider than the element, it pans left underneath a pinned caret.

Install

<script src="type-pan.js"></script>

Injects its own <style> tag (layout height, viewport clipping, blink keyframes) on first use, so no companion CSS file is required. The downloaded file is self-contained - it bundles three small shared dependencies: hover-scroll-source.js ("static scroll" mode's wheel-target wiring), sequence-stepper.js (the animated-step engine behind 'continuous' driveMode and .nextChar()/.prevChar()/ .nextWord()/.prevWord() below), and scroll-progress.js (the scroll-position math behind 'scroll' driveMode), all shared with Rolodex.

Usage

<div class="type-pan" data-text="Scroll to reveal the whole headline">
  Scroll to reveal the whole headline
</div>
<script src="type-pan.js"></script>

Reads data-text or trimmed textContent. Auto-initializes against every .type-pan element. To switch drive mode and configure options: 

TypePan.initAll('.type-pan', {
  sensitivity: 1,
  panPosition: 0.65,
  driveMode: 'continuous',
});

Options

OptionDefaultDescription
driveMode 'scroll'
  • 'scroll' — real page scroll position drives typing, reversible/scrubbable like the other scroll-linked effects
  • 'continuous' — self-animating type/hold/erase clock
  • 'hover' ("static scroll") — the element stays put on the page; wheel/trackpad input over it (or over an element tagged data-type-pan-hover="<that element's id>") drives typing directly instead of scrolling the page

lag0.18Smoothing (0–1) applied to pan movement; higher is snappier

cursorBlinktrueWhether the caret blinks
sensitivity1Multiplier applied to wheel delta before it becomes typing progress (hover mode)
typeDuration2200ms to type the full line (continuous mode)
holdDuration1000ms held fully typed before erasing (continuous mode)
rollbackSpeed700ms to erase back to empty (continuous mode)
stepSpeed60ms per character for .nextChar()/.prevChar()/.nextWord()/.prevWord()/.goTo() - a constant pace, so a bigger step just takes proportionally longer than a single-character one
stepPolicy 'redirect' What .nextChar()/.prevChar()/.nextWord()/.prevWord()/.goTo() do if called again before the current step lands - see the Methods section below.
  • 'redirect' — retargets immediately from wherever the reveal visually is; a fast burst blurs past every character in between
  • 'rateLimit' — drops a call arriving less than minStepInterval after the last one accepted
  • 'queue' — lets the current step finish, then plays queued calls back-to-back in order
minStepInterval150ms - only meaningful with stepPolicy: 'rateLimit'

Methods

.nextChar() / .prevChar() reveal or erase one more character; .nextWord() / .prevWord() do the same through to the next/previous word boundary; .goTo(targetCount) reveals (or erases back) directly to an arbitrary character count. All animate through every character in between at stepSpeed - typing/backspacing, never an instant jump, so a big goTo() jump visibly types/erases through everything in between rather than blurring past it (pass { duration } to use a fixed total time instead, regardless of distance). They work alongside 'scroll'/'hover' driveMode: scrolling or wheeling again immediately takes back over from wherever the step landed. What happens if one of these is called again before the last one finished is governed by stepPolicy above - worth trying out on the demo page, which has a Next/Prev word button and a live Step policy switch.

.pushProgress(value) feeds in a 0–1 reveal fraction from any custom source, exactly as real page scroll and hover-wheel input do internally - this is what the homepage's carousel card uses instead of the page scrolling to drive its Type Pan, and is the general escape hatch for tying typing to anything other than the page or an element tagged data-type-pan-hover. Unlike Rolodex's pushProgress(), values are always clamped to 0–1 - there's no circular "loop past the end" for a single line of text.

Notes

In hover mode the element (or its data-type-pan-hover target) captures wheel events with { passive: false } and calls preventDefault(), so the page won't scroll while the pointer is over it. Call .reset() on an instance to reset hover-mode typing progress back to the start; .setText(value) replaces the line being typed (rebuilds the character spans and word boundaries, resetting progress). TypePan.get(elOrSelector) / TypePan.getAll(selector) look up already-initialized instances, and .destroy() tears one down (stops its animation loop and removes all listeners).

Flip Dots

A programmable grid of physical discs on a canvas. Each one sits on a center axle: asked for a new state it turns a half turn, slams into its magnet stop, and the color you see swaps at the exact moment it passes edge-on. That last detail is what lets a dot hold any number of colors without lying about the metaphor - a real disc has two faces, but nobody ever sees the back of one, so repainting the far face mid-turn is invisible and any state can reach any other in a single flip.

Write single dots, whole grids, patterns or text. Who flips when is a separate question from how a dot moves, and both are open: a registry of transitions decides the order, a registry of easings decides the pace, and either takes a function of your own.

Install

<script src="flip-dots.js"></script>

One script tag, no dependencies and no companion CSS - it injects its own <style> defining .flip-dots and the canvas inside it, and auto-initializes every matching element on load. The host supplies the box; the component measures it and lays a grid out inside.

Quick Start

<style>
  .my-board { width: min(720px, 92vw); aspect-ratio: 16 / 9; }
</style>

<div class="flip-dots my-board" id="board"></div>
<script src="flip-dots.js"></script>
<script>
  const board = FlipDots.get('#board');
  board.text('HELLO', { transition: 'ripple' });
</script>

Give the element a width and a height - everything else is derived from that box. With no cols the grid is measured against dotSize; with cols set, the dot size is measured against the grid. Cells are always square, and the grid is centered in whatever slack is left over. 

FlipDots.initAll('.flip-dots', {
  cols: 60,
  palette: ['#1b1e24', '#f0ece2'],
});

Recipes

Writing to the board

set() writes one dot and flips it immediately - that's a dot being poked, and poking it should land now. setGrid() writes the whole board and gets a transition, because that's a new frame of content arriving. The difference in treatment is the whole reason they're separate calls. 

board.set(4, 2, 1);                 // one dot, no choreography
board.fill(1);                      // every dot
board.clear();
board.rect(0, 0, 8, 8, 1);
board.setGrid(grid, { transition: 'wipe' });

setGrid takes a 2D array, a flat row-major array, a function, or an array of strings - the string form being there because a pattern someone typed by hand is the common case, and it stays readable where nested arrays of integers do not. Cells outside the data are left alone, so a small pattern written to a big board changes only the dots it covers. 

board.setGrid([
  '..##..',
  '.####.',
  '######',
], { charMap: { '.': 0, '#': 1 } });

Only dots whose state actually differs will flip. Writing the same frame twice is free, and changing one word to another on a message board costs the handful of discs that disagree rather than the whole board.

Driving one dot yourself

set() takes the same four questions a transition answers for a whole board, so hand-rolled choreography is not a lesser path - a transition is just a convenient way to generate delay for every dot at once. 

board.set(4, 2, 1, {
  delay: 120,          // ms before this dot starts
  flipDuration: 300,   // this dot's own half turn
  bounce: 0.9,         // how hard this one rings
  direction: -1,       // force the turn direction
  silent: true,        // no click from this one
});

The same keys work on setGrid, where they apply to every dot of that update. Note duration is the spread - how long the whole update takes to roll out - and flipDuration is one dot's own turn. They're independent, which is what lets a slow wave be made of fast flips, or a fast wave of slow ones. 

board.setGrid(grid, { transition: 'rows', duration: 1600, flipDuration: 90 });

direction is the one worth knowing about. Normally a dot's turn direction comes from comparing palette indices, which reads well when the palette is a scale (dark to light) and means nothing when it isn't (red, blue, yellow). Forcing it lets a whole wave turn the same way regardless of what colors are involved - as does directional: false on the board.

Knowing when it has landed

How long an update takes is duration plus a flip plus whatever ringing bounce adds plus per-dot jitter - not a sum worth reconstructing with setTimeout. The board says so itself. 

board.el.addEventListener('flip-dots:settle', () => {
  board.setGrid(nextFrame, { transition: 'shuffle' });
});

board.settled            // nothing is moving
board.isAnimating(4, 2)  // is this dot mid-flight?
board.settle();          // cut the current update short

The event marks a transition rather than a state: it fires once when the board goes from moving to still, and a board that is already still stays quiet however many times it's ticked, settled or scrolled back into view. For per-dot granularity there is onFlip, which is a plain callback rather than an event because a board-wide wave is thousands of them in a single frame.

Flip time and bounce

The spring has exactly two numbers and they divide cleanly. bounce decides what the motion looks like; flipDuration decides how fast that same motion plays. That separation is exact rather than approximate - the trajectory depends on the damping ratio alone, and the spring constant does nothing but scale the time axis - so changing the duration gives you the identical flip sped up or slowed down, and changing bounce gives you a different flip. 

// Same character, half the time
FlipDots.initAll('.flip-dots', { flipDuration: 65, bounce: 0.55 });

// Same timing, far rattlier
FlipDots.initAll('.flip-dots', { flipDuration: 130, bounce: 0.95 });

Which is why stiffness is not a third control - it is flipDuration in spring units, and setting it ignores the duration. The component works the constant out for you, and springConstant reads back the answer.

One honest limit at the quiet end: as bounce approaches 0 the spring barely crosses its target at all, so the constant needed to arrive by a deadline runs away faster than the integrator can follow. Below about bounce: 0.2 a short flipDuration becomes a request rather than a guarantee, and the dot may take a little longer than asked.

Any number of colors

A dot's state is an index into palette, so colors are a lookup rather than a property of the data - re-theming a board is a palette swap with no change to what's written on it. There is no two-color limit; a disc shows the face it is turning toward, and that face is painted while it is edge-on and invisible. 

FlipDots.initAll('.flip-dots', {
  palette: ['#1b1e24', '#f0ece2', '#e8503a', '#ffc247'],
});

A palette entry may be an object instead of a color string, which is how one state gets a rim the others don't - a faint socket ring on "off" dots while the lit ones stay clean. 

palette: [
  { fill: '#0f1115', border: 'rgba(255,255,255,0.12)' },
  '#f0ece2',
]

Dots that materialize out of nothing

Rims are off by default for exactly this: set state 0 to the page color behind the board and an "off" dot is invisible, so content appears out of blank paper rather than lighting up inside a visible socket. background: null leaves the canvas transparent, so the board can sit over whatever is already there. 

FlipDots.initAll('.flip-dots', {
  background: null,
  palette: ['#ffffff', '#111111'],
});

Who flips when

A transition answers one question per dot: how far into the update does this one start. That's the whole contract - (x, y, ctx) => 0..1 - which is why everything from a wipe to a scatter to a spiral is a different answer to it rather than a different mechanism. duration is the spread in milliseconds from the first dot starting to the last, and is independent of how long one flip takes: a long spread of fast flips is a travelling wave, a short spread of slow ones is the whole board turning at once. 

board.setGrid(grid, { transition: 'ripple', duration: 700 });
board.setGrid(grid, { transition: 'wipe', direction: 'up' });

// Ripple out from the dot someone just clicked
board.el.addEventListener('click', (e) => {
  const at = board.dotAt(e.clientX, e.clientY);
  if (at) board.setGrid(grid, { transition: 'ripple', origin: at });
});

Register your own and it has the same standing as the built-ins: 

FlipDots.transitions.register('spiral', (x, y, g) => {
  const dx = x - g.cols / 2;
  const dy = y - g.rows / 2;
  const angle = (Math.atan2(dy, dx) + Math.PI) / (Math.PI * 2);
  return (angle + Math.hypot(dx, dy) / g.cols) % 1;
});

board.setGrid(grid, { transition: 'spiral' });

How the clock runs while it plays

The transition says what order the dots go in; easing says how fast the clock moves through that order. Keeping them apart means four easings across nine transitions is thirty-six looks out of thirteen small functions, instead of needing a ripple-decelerating entry sitting next to ripple. 

// Off hard and winding down
board.setGrid(grid, { transition: 'wipe', easing: 'decelerate' });

// A slow start that finishes in a rush
board.setGrid(grid, { transition: 'rows', easing: 'accelerate' });

FlipDots.easings.register('bounce', (t) => t * t * (3 - 2 * t));

The curve is easier to read backwards: where the output changes slowly, many dots start close together and the wave is moving fast; where it changes quickly, they're spread out and it's moving slowly.

Text

text() writes a line across the whole board in a 5×7 bitmap font - lit dots for the glyphs, the off state everywhere else, centered unless x/y say otherwise. It goes through setGrid, so a message arrives on a transition like anything else. 

board.text('GATE 7', { transition: 'rows', easing: 'decelerate' });
board.text('14:05', { on: 2, spacing: 2 });

measureText() returns the width in dots, for deciding whether a message fits before committing to it. Derive the limit from the live grid rather than writing it down - the grid is measured against the element's box, so a hardcoded character count is wrong on every window but the one it was written on. 

const perGlyph = FlipDots.font.width + 1;
const fits = Math.floor((board.cols + 1) / perGlyph);

The hinge

hinge is the angle of the axle each disc turns on, in degrees. 0 lays it flat so the disc tumbles top over bottom, 90 stands it upright so it swings like a door, and anything between is a diagonal. Only 0-180 exists: an axle has no near end and far end, so 190 is the same hinge as 10. 

FlipDots.initAll('.flip-dots', { hinge: 90 });  // swings like a door
FlipDots.initAll('.flip-dots', { hinge: 45 });  // diagonal

Sound

Off by default - a component that starts making noise in someone else's page has to be asked for. Switched on, each disc clicks as it meets its stop, synthesized rather than loaded from a file. Browsers won't start audio before a real user gesture, so turning it on arms the audio for the next pointer or key event; enableSound() is for the case where the gesture has already happened, such as your own "sound on" button. 

FlipDots.initAll('.flip-dots', { sound: true, volume: 0.4 });

soundButton.addEventListener('click', () => board.enableSound());

A board-wide wave is thousands of flips, which as thousands of voices would be white noise and more than the audio thread will schedule. Clicks landing in the same instant are collapsed into a few louder voices, panned toward where on the board they happened - which is the difference between a wave that clatters and one that hisses.

As a background

The canvas inserts itself as the element's first child, behind everything else in it, so a board can carry its own content. With the lit state held well down from full brightness the text on top stays the brightest thing on it. 

<section class="flip-dots hero">
  <h1>Anything you like</h1>
</section>

Notes

The color swaps at edge-on, which is what makes N colors work: a dot carries a face for even half turns and one for odd, and which you see is decided by the parity of the nearest flat position. Painting the other parity's face is therefore always invisible. Asked for a new state mid-flight, a dot still short of edge-on hasn't revealed its destination face yet, so the new state simply overwrites it and the dot carries on with its momentum intact; past edge-on it has to turn again - and if the new state is the one it was leaving, it springs back the way it came rather than continuing round.

It's a spring against a magnet stop, not a tween: travel past the target is capped at overshoot and what velocity is left rebounds, so the overshoot you see is the disc flexing against its stop rather than swinging past it. The spring is integrated at a fixed sub-step regardless of frame rate, so the feel is identical on a 60Hz and a 144Hz display and a dropped frame can't fling a dot. At the defaults a disc reaches its stop in about 127ms and has finished ringing by about 430ms.

The disc has a rim, and it matters more than it sounds: without one a face just darkens as it turns, and a dark face on a dark panel darkens straight into invisibility - so half of every flip is a dot quietly vanishing and the other half is a different dot appearing, which is the one thing a flip must not look like. A rim that is neither of the two faces keeps the disc continuously visible all the way round. edgeColor defaults to the palette's own average mixed toward black, so it stays visible against both the darkest face and the lightest without being set.

A dot never leaves its cell, and the repaint depends on it: only cells that moved are redrawn, each clearing exactly its own cell and nothing more - which is only safe because the perspective lean is capped at the cell's own slack and, on a diagonal hinge, non-circular shapes are clipped to their cell. A padded clear would reach into neighbors and shave the dots already drawn there. One consequence worth knowing: at gap: 0 there is no slack, so perspective has no room to do anything.

Cell boundaries are snapped to whole device pixels: computed from a fractional center and a width, each dot's edges land mid-pixel and antialias against the background, and a board of square dots at zero gap draws a grid of seams over itself. Insetting from a shared snapped boundary means neighbors agree exactly where the edge between them is.

The loop stops when the board is at rest: requestAnimationFrame runs only while something is mid-flight and tears itself down otherwise, so a settled board costs nothing at all. It also pauses off screen, and snaps everything to its target on the way out rather than replaying a queue of stale delays on the way back.

Resizing resamples rather than clearing: a new grid is filled nearest-neighbor from the old one and lands settled and flat, so dragging a window doesn't blank the board - or fire a board-wide flip, and a board-wide clatter, on every frame of the drag.

There is a floor on dot size: below about five pixels the squash that carries the whole effect happens inside a pixel or two and stops reading as rotation, so a grid that fine is thinned rather than drawn that small. Read cols and rows back for what you actually got.

Reduced motion is honored: under prefers-reduced-motion states change instantly with no rotation, and the component follows a live change to the setting rather than only reading it once.

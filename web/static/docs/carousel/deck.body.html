Carousel · Click / Scroll / Swipe

Deck

A frame changer. One box, a stack of frames inside it, and a transition that decides what the move from one to the next looks like — a slide, a crossfade, a cube face turning, a card dealt off the top, or the arc of a View-Master reel. Everything else is the same whichever you pick: click, scroll, swipe, arrows, dots, keyboard, autoplay, the lot. Six transitions ship with it, and writing a seventh is a dozen lines.

Install

<script src="deck.js"></script>

One script tag and nothing else. The deck shares its wrap-around arithmetic, its per-tab position memory and its initAll/get/getAll surface with the other three carousels here, and the file above already has that bundled in - so there is nothing extra to fetch. (Building from this repo's own source instead, that part is shared/carousel-kit.js, loaded before deck.js.) Injects its own <style> tag defining .deck, .deck-port and .deck-frame plus the controls it builds for itself, so no companion CSS file is required.

Quick Start

<div class="deck" data-transition="slide">
  <div class="deck-port">
    <div class="deck-frame"><img src="1.jpg" alt="" /></div>
    <div class="deck-frame"><img src="2.jpg" alt="" /></div>
    <div class="deck-frame"><img src="3.jpg" alt="" /></div>
  </div>
</div>
<script src="deck.js"></script>

That is a complete, working carousel — arrows, dots, click, drag, sideways scroll and the arrow keys, at a sensible size, with no CSS and no JavaScript of your own. Auto-initializes against every .deck:not(.is-empty) element. Only direct children of .deck-port carrying .deck-frame count as frames, and anything hidden is skipped. A frame is an empty box that fills the deck, so put whatever you like in one: a single <img> or <video> is made to fill it for you, and anything else is yours to style. 

Deck.initAll('.deck', {
  transition: 'cube',
  duration: 420,
});

Transitions

Name one in markup with data-transition, or pass it as the transition option. Switching at runtime — deck.update({ transition: 'fade' }) — is safe at any time, including mid-move.

TransitionDragOwn optionsDescription
slidescrubsgapFrames side by side on a line. The default, and the only one where gap is literally empty space
fadescrubs—A crossfade that never dips through the background (see the notes)
zoomscrubszoomScaleThe same crossfade with scale on it: the arriving frame grows into place, the leaving one pushes past
stackscrubsstackInset, stackOffset, stackScale, stackFade, stackTiltA dealt deck. The only built-in that shows more than two frames at once, and the only one where the frame in view doesn't fill the box
cubescrubs—Faces of a box turning about its vertical axis. Sets perspective on the port itself
stereoscoperatchetsarc, gapThe View-Master: frames mounted radially on a disc whose pivot is off screen below the deck

Scrub or ratchet. Five of the six track a drag 1:1 and settle where you let go, carrying on to the next frame if you flick. stereoscope doesn't, because a frame parked halfway through an arc isn't a pose anything can rest in — a drag there gives by a fifth of a step and then either commits a whole frame or springs back. Every other input moves in whole frames regardless.

Transition options belong to the transition. gap means reel material to the arc, dead space to a slide, and nothing at all to a crossfade — so each transition declares its own defaults, and switching transitions re-seeds them. An option you set yourself survives for as long as the transition that owns it is running.

Writing One

The whole engine runs on a single number: delta, a frame's signed, wrapped distance from the position in view (0 is in view, +1 is one ahead, -0.5 is halfway out backward). A transition is that number turned into appearance, and nothing else: 

Deck.transitions.flip = {
  scrub: true,                  // can a drag track it 1:1?
  cull: 1.05,                   // hide frames further out than this
  defaults: { flipTilt: 90 },   // options this transition owns
  measure(ctx, frames) {        // optional: re-derive on resize
    ctx.port.style.perspective = `${Math.round(ctx.w * 2)}px`;
  },
  style(frame, delta, ctx) {    // required: paint one frame
    frame.style.transform =
      `rotateX(${(-delta * ctx.options.flipTilt).toFixed(2)}deg)`
      + ` translate3d(0, ${(delta * 100).toFixed(2)}%, 0)`;
  },
  setup(ctx) {}, teardown(ctx) {},   // optional: per-instance DOM/CSS
};

<div class="deck" data-transition="flip">…</div>

Register it before the deck initializes (a plain <script> after deck.js is early enough) and it is indistinguishable from a built-in — the markup can name it, the options panel can tune it, and it inherits every control, input mode and accessibility behaviour on this page. You can also pass a transition object inline as the transition option without registering it at all.

MemberDescription
style(frame, delta, ctx)Required. Sets the frame's appearance for that distance. Called for every non-culled frame on every animation tick.
measure(ctx, frames)Called on init, on resize, and whenever an option changes. The place for anything derived from the box's pixel size — a transform-origin, a perspective, a cached angle on ctx.state.
setup(ctx) / teardown(ctx)Called when the transition is attached to and detached from an instance. Frame styles are reset for you between transitions; anything you put on the port is yours to clean up.
defaultsOptions this transition owns, merged under the host's own values. Also what the demo page reads to know which sliders to show.
scrubfalse makes a drag ratchet rather than track. Default true.
cullFrames further out than this many steps are hidden. Default 1.6 — raise it for a transition that shows a pile.
ctx{ root, port, w, h, options, state, dir }: the elements, the measured box, the resolved options, a scratch object of your own, and the direction of travel (+1, -1, or 0 at rest).

One constraint: a frame's z-index must stay below 200. The port isn't a stacking context of its own, so a frame competes with the glare overlay at 200 and the controls at 250 rather than only with its sibling frames.

Sizing

A deck is width: 100% at aspect-ratio: var(--dk-aspect, 3 / 2), so it fills whatever you put it in and keeps its shape at every width. Sizing one is two decisions, both on your side of the line — the component has no size options at all: 

.my-deck {
  --dk-aspect: 16 / 10;   /* the shape */
  max-width: 680px;       /* how big it may get */
}

/* Or ignore the ratio entirely - an explicit height wins. */
.my-banner { height: 320px; }

Nothing inside needs to change when it resizes. Frames fill the deck by definition, every transition re-measures itself from a ResizeObserver (so a sidebar opening or a font loading is handled, not just a window resize), and the arrows and dots shrink their own hit targets below 400px with a container query. .deck is itself a container-query context, so frame content sized in cqw tracks the deck rather than the viewport: 

.my-caption { font-size: 4cqw; padding: 6cqw; }

Controls

Out of the box: prev/next arrows, a row of dots, click or tap to advance (shift-click to go back), drag, horizontal wheel or trackpad, and ← → ↑ ↓ Home End on the keyboard. Turn any of it off with arrows, dots, click, drag and wheel.

Beyond that, any element on the page can drive a deck with no JavaScript — one delegated listener handles all of them, however many decks are on the page and whenever the elements appear. The built-in arrows and dots are nothing but these same hooks.

AttributeDoes
data-deck-nextAdvances one frame on click
data-deck-prevGoes back one frame on click
data-deck-to="N"Goes to frame N by the shortest way around
data-deck-leverTurns the element into a pull lever (drag down, or tap)
data-deck-for="#id"Points a hook — or a whole container of them — at a deck it isn't inside
data-transitionOn the deck itself: which transition to start with
 
<div class="deck" id="tour">...</div>

<!-- Anywhere on the page -->
<div class="my-rail" data-deck-for="#tour">
  <button data-deck-prev>Back</button>
  <button data-deck-to="0"><img src="1-thumb.jpg" alt="" /></button>
  <button data-deck-to="1"><img src="2-thumb.jpg" alt="" /></button>
  <button data-deck-next>Forward</button>
</div>

A hook inside a deck needs no data-deck-for — it drives the deck it sits in. Outside one, put data-deck-for on the hook itself or on any ancestor of it. These hooks fire on click, so use a real <button> — the keyboard and assistive technology get that for free, and nothing is added for you. (data-deck-lever is the exception: it's a drag gesture rather than a click, so a non-interactive element carrying one does get role="button" and a tab stop.)

Recipes

Carrying text rather than pictures

The defaults are tuned for images. Copy wants a longer step, no rebound (text that overshoots and settles is hard to start reading) and usually a crossfade rather than anything with geometry in it. 

Deck.initAll('.testimonials', {
  transition: 'fade',
  duration: 460,
  bounce: 0,
});

Cards on the page, not in a box

stack holds the whole pile in from the edges by stackInset, because a card that covers every pixel leaves nothing for the ones behind it to peek out of — so what surrounds it is --dk-body, the deck's own background. Leave that dark and it reads as cards in a window. Make it transparent and turn clip off and the same transition reads as loose cards lying on the page: nothing behind them, and nothing stopping the thrown one from leaving the box. Give the frames a background and a shadow of their own, since there's no longer a deck behind them, and leave room below the deck for the pile to hang into. 

<div class="deck my-cards" data-transition="stack">…</div>

<style>
  .my-cards { --dk-body: transparent; margin-bottom: 4rem; }
  .my-cards .deck-frame {
    background: #fff;
    border-radius: 10px;
    box-shadow: 0 10px 28px rgba(0, 0, 0, .16);
  }
</style>
<script>Deck.initAll('.my-cards', { clip: false });</script>

clip: false is only sensible for a transition that keeps its frames near the box and fades them out before they leave it — which stack does, reaching zero opacity exactly one frame out for this reason. Turn it off under slide or stereoscope and you'll see the entire strip of frames spread across the page at once.

Making scroll the primary driver

wheel: 'x', the default, takes only horizontal deltas — a two-finger sideways trackpad gesture — so a vertical scroll always passes straight through to the page. A plain mouse wheel produces no horizontal delta at all, so on a desktop with a mouse the primary driver is the click. If you want the wheel itself to drive a deck, 'any' takes vertical deltas too, at the cost of capturing page scroll while the pointer is over it — reasonable for a full-height hero, bad for a carousel halfway down a long article. 

Deck.initAll('.hero-deck', { wheel: 'any' });
Deck.initAll('.inline-deck', { wheel: false });

A slideshow that runs itself

autoplay is milliseconds between automatic steps. It pauses while the deck is off screen, while the tab is hidden, while the pointer is over it, and while anything inside it has focus — and it skips a beat rather than restarting its interval, so the cadence stays steady across a hover that begins and ends mid-interval. It stays off entirely under prefers-reduced-motion: reduce. 

Deck.initAll('.deck', { transition: 'zoom', autoplay: 3200 });

// Drive the timer directly - the option stays as it was.
const deck = Deck.get('#myDeck');
deck.pause();
deck.play();

A deck with two ends

A deck loops by default — the last frame advances to the first and there is no beginning or end. loop: false gives it two: the position clamps, frames stop wrapping round to the other side (so the far end stays culled out of sight instead of queueing up on the near one), the arrows go disabled where there is nothing left to show, and a wheel that can't move the deck any further is handed back to the page rather than captured — which is the one escape hatch wheel: 'any' otherwise doesn't have.

The root also carries .is-at-start and .is-at-end at those two points, for styling of your own — a counter, a hint, a different treatment for the dead arrow than the built-in dimming.

Reaching the end matters most to autoplay, which would otherwise press silently against it forever, so autoplayEnd says what happens there: 'rewind' (the default) sweeps back through every frame to the first, 'bounce' reverses and walks back a frame per beat, 'jump' waits one beat and cuts back to the first, and 'stop' parks there — though even then the timer keeps running, so advancing the deck off the end by hand has it pick up again. 

// Runs through once, then cuts back and does it again
Deck.initAll('.deck', { loop: false, autoplay: 3200, autoplayEnd: 'jump' });
.deck.is-at-end .my-hint { opacity: 1; }

A lever of your own

lever: true draws the built-in one in the bottom-right corner. Any element carrying data-deck-lever is used instead, and gets the same gesture: while a pull is live the component puts --dk-pull (0 to 34deg) on that element and adds .is-pulling to it — which is everything your CSS needs. A tap on a lever advances too, so it never demands a drag. 

<span class="my-lever" data-deck-lever data-deck-for="#tour"><i></i></span>

<style>
  .my-lever { touch-action: none; } /* so a pull isn't also a page scroll */
  .my-lever i {
    transform-origin: 50% 100%;
    transform: rotate(var(--dk-pull, 0deg));
    transition: transform 220ms cubic-bezier(.22, 1.4, .4, 1);
  }
  .my-lever.is-pulling i { transition: none; }
</style>

Reacting to the frame in view

Listen for the bubbling deck-settle event instead of polling .index — it fires once a frame is actually parked, not for every frame passed on the way there, so a five-frame jump produces one event rather than five. The demo's caption is driven entirely by it. 

document.getElementById('tour').addEventListener('deck-settle', (e) => {
  caption.textContent = e.target.dataset.title;
});

Notes

One number runs everything. Position is a float in frames, integer at rest, and a frame's appearance is a function of its wrapped distance from it. That is why a transition is a dozen lines rather than a fork of the component, why switching one mid-move is safe, and why a drag can scrub: the model has no notion of "between slides" to be confused by.

Why the crossfade never dips. The obvious implementation ramps both frames to 50% at the midpoint, which leaves two half-transparent layers over the deck's background and reads as a flash of the body color. Instead the arriving frame fades in over an outgoing one left at full opacity. A pleasant consequence: if the direction of travel flips mid-move — a scrub released backward — the two swap roles with no visible jump, because a over opaque and 1 − a the other way composite to exactly the same pixels.

The arc's pitch is derived, not configured. For stereoscope, the angle between frames falls out of the measured width and the disc radius, as the angle whose chord spans one frame width plus gap — the chord rather than the arc, because the chord is how far apart the frame centers actually sit on screen. At arc: 0.5 the radius is 2.4 deck widths and the pitch lands near 26°, which is a real View-Master reel's 360/14. Some black always shows between frames there, even at gap: 0: the frames share one pivot, so they meet at the height of their centers and wedge apart above and below it. That wedge is why a real reel has opaque cardboard between its frames at all.

The loop parks itself. Nothing settles asymptotically, so there's no reason to keep ticking between moves. The animation loop runs only while a move is playing, a drag is live, or leftover play is still decaying, and cancels itself otherwise — so an idle deck costs nothing. An IntersectionObserver stops it off screen as well, mostly to gate autoplay.

Only the frame in view is interactive. Every other frame gets inert and pointer-events: none, and nothing at all is interactive while the deck is moving. A link half way out isn't a link anyone meant to click, and the ones fully out are off screen — so leaving them focusable would put several invisible copies of the same tab stop in the page. Frames beyond the transition's cull distance are hidden outright, which keeps a 40-frame deck from compositing 40 layers to paint one.

Click is the primary driver on purpose. It is the one input every device has. A mouse has no horizontal wheel, a trackpad has no detents, a phone has neither — so a tap advances, the arrows cover backwards, and drag, wheel and the arrow keys are each an addition rather than the only way through. Only the primary button counts: a press that advanced the deck on a right- or middle-click would be advancing it while the visitor was reaching for a context menu.

The arrow keys stand down inside a form field. tabindex="0" and role="group" go on the root unless the host set them, and Left/Right/Up/Down plus Home/End drive the deck — except when the key press landed in a text field, a <select> or a contenteditable region inside the frame in view. A frame can hold anything, and in there those keys belong to the caret, not to the deck.

Position is remembered per instance, per tab. The parked frame's index is written to sessionStorage, keyed by the root element's own id, and restored once on an instance's first refresh(). A deck with no id doesn't persist.

Reduced motion. Under prefers-reduced-motion: reduce a move becomes an instant cut with no overshoot, the lever stops animating, and autoplay stays off however it's configured. The media query is read live, so a visitor changing the setting doesn't need a reload.

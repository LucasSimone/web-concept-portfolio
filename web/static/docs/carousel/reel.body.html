Reel

A View-Master-style carousel. Cards sit on a ring that curves back and away behind a single focus point, dead center - the focused card grows to full size exactly as it arrives there, rather than sliding into a separately-sized center slot, while the rest curve off into a halo behind it, shrinking and fading the further round they sit. By default there's no first or last card - spin it either direction as far as you like, same as a real reel's click wheel never runs out of rotation - and loop: false gives it two ends to stop against instead.

Install

<script src="reel.js"></script>

One script tag and nothing else. The ring shares its wrap-around arithmetic, its per-tab position memory and its initAll/get/getAll surface with the other three carousels here, and the file above already has that bundled in - so there is nothing extra to fetch. (Building from this repo's own source instead, that part is shared/carousel-kit.js, loaded before reel.js.) Injects its own <style> tag defining .reel, .reel-track and .reel-card, so no companion CSS file is required - but the host still supplies its own size and card chrome (width, height, border, background, and whatever's inside it).

Quick Start

<style>
  .my-reel { width: min(600px, 92vw); aspect-ratio: 600 / 500; }
  /* cqw = 1% of the reel's own width, so cards scale with the ring */
  .my-reel .reel-card { width: 33.3cqw; height: 38.3cqw; }
</style>

<div class="reel my-reel">
  <div class="reel-track">
    <div class="reel-card">One</div>
    <div class="reel-card">Two</div>
    <div class="reel-card">Three</div>
  </div>
</div>
<script src="reel.js"></script>

Auto-initializes against every .reel:not(.is-empty) element. Give the root both a width and a height - unlike Sweep's flat strip, the ring needs room above and below the focused card as well as to its sides, and both radii are measured off this box. Every direct child of .reel-track is treated as a card regardless of its own class, but .reel-card is what the injected CSS positions.

Card size is the host's and the ring's radii are measured off the root's box, so the two don't track each other automatically - fixed-pixel cards on a fluid reel take up more and more of the ring as it shrinks. .reel is a container-query context, so sizing cards in cqw (1% of the reel's own width) keeps them proportional at any size. To configure options: 

Reel.initAll('.reel', {
  cardAngle: 24,
  minScale: 0.2,
});

Recipes

How big the ring is

The ring is fitted to the root's box by default - as wide and tall as it can be while still leaving the focused card room to sit at full size inside it - so CSS sizing the element is normally all it takes and the whole thing stays responsive for free. ringSize scales that fit, and is deliberately not clamped above 1: a ring wider than its own window is a legitimate look, not a mistake. 

// Drawn in tight around the focus
Reel.initAll('.reel', { ringSize: 0.6 });

// Swung out past the box's own edges
Reel.initAll('.reel', { ringSize: 1.3 });

radiusX and radiusY read the effective radii back in pixels, after fitting and scaling - useful for a UI reporting what's actually being drawn rather than what was asked for.

A loop, or an arc with two ends

loop is on by default: card distances wrap at the card count, _pos is never clamped, and the ring turns forever in either direction. Off, distances stop wrapping and position is clamped to the first and last card, so what's left reads as an arc that runs out - and wheel capture is handed back at either end the way Sweep's strip does, so a scroll that can't turn the ring any further carries on down the page. 

// A fan of cards with a beginning and an end
Reel.initAll('.reel', { loop: false, maxDepth: 0.7 });

Which scroll axis spins it

wheelAxis is Dial's control exactly, with the same trade-off. 'both' (the default) assigns each event to whichever axis dominates it, which is what makes one ring work for a mouse wheel - which only ever reports deltaY - as well as a trackpad; the cost is that taking the vertical axis means calling preventDefault on it, so the page stops scrolling while the pointer is over a looping ring. 'horizontal' never interferes with the page, but then a mouse wheel does nothing. A large ring sitting partway down a long page usually wants 'horizontal'; a deliberate widget the visitor came to use can take both. 

// Never interrupts page scroll
Reel.initAll('.reel', { wheelAxis: 'horizontal' });

// Only a mouse wheel / vertical trackpad gesture
Reel.initAll('.reel', { wheelAxis: 'vertical' });

Turning by itself

autoplay is milliseconds between automatic steps, 0 for off. It pauses while the pointer is over the ring, while it's being dragged or actively scrolled, while it's off screen, in a hidden tab, or under prefers-reduced-motion - so a ring that turns itself still holds still for anyone actually reading it, with nothing to wire up.

A looping ring simply turns forever. With loop off there is a last card to reach, and autoplayEnd is what happens there: 'rewind' (the default) spools back round through every card to the first, 'bounce' reverses and walks back a card per beat, 'jump' waits one beat and cuts back to the first, and 'stop' parks there - though even then the timer keeps running, so spinning the ring off the end by hand has it pick up again. 

Reel.initAll('.reel', { autoplay: 2200 });

// An arc that runs to the end, then spools back and does it again
Reel.initAll('.reel', { loop: false, autoplay: 2200, autoplayEnd: 'rewind' });

// Or drive the timer directly - the option stays as it was.
const ring = Reel.get('#myReel');
ring.pause();
ring.play();

Spinning it from your own code

Everything the wheel, a drag, a click or the arrow keys can do is on the instance too, in two flavours: .step(), .next(), .prev(), .to(), .first() and .last() all spin there with the same settle spring the input modes use, while .jump() cuts straight to a card with no spin at all. .index and .length read back where it is. A row of buttons, a keyboard shortcut of your own, or a ring driven entirely by something else on the page is wiring, not a fork. 

const ring = Reel.get('#myReel');

document.querySelector('.next').onclick = () => ring.next();
document.querySelector('.prev').onclick = () => ring.prev();
document.querySelector('.home').onclick = () => ring.first();

// No spin - straight there, as if it had always been on that card.
ring.jump(4);

A denser or sparser ring

cardAngle is degrees of rotation per card step - the one control that most changes how the ring reads. Low values pack many cards into view at once, each only a short step apart; high values spread them out, so fewer are visible before they swing past the point directly behind the focus. 

// A dozen cards crowded into a tight ring
Reel.initAll('.reel', { cardAngle: 18 });

// A wide, open fan - only a couple of neighbors visible at a time
Reel.initAll('.reel', { cardAngle: 55 });

How much of the background stays visible

maxDepth is where a card fades out entirely, in depth units (0 at the focus, 1 directly behind it). Paired with minScale - how small a background card ever gets - these two together are what make a card count sit comfortably on the ring without turning into visual noise: a high maxDepth keeps nearly the whole ring populated, a low one declutters down to just the focus and its nearest neighbors. 

// Keep almost the entire ring visible, very small in the back
Reel.initAll('.reel', { maxDepth: 0.98, minScale: 0.1 });

// Only the focus and its immediate neighbors show at all
Reel.initAll('.reel', { maxDepth: 0.55 });

Snappier or lazier

Exactly Sweep's friction / snapStrength pair: friction decays velocity each frame once input goes idle, snapStrength is the constant pull toward the nearest card folded in on top of that decay. 

Reel.initAll('.reel', { friction: 0.95, snapStrength: 0.09 });

Turning off an input mode

wheelEnabled and clickToSelect each turn off one way of spinning the ring, independently of each other - drag and the arrow keys always stay live. 

// Drag, click and keys only - a scroll over the ring does nothing
Reel.initAll('.reel', { wheelEnabled: false });

// A card's own links fire on the first click, wherever it sits
Reel.initAll('.reel', { clickToSelect: false });

With clickToSelect on (the default), a click on a card that isn't in focus spins it there by the shortest way round and is swallowed; a click on the focused card passes straight through to whatever is inside it. So a card full of links behaves like "bring it to the front, then use it" rather than needing a separate control - the same rule as Dial's gate.

Reacting to the focused card

Listen for the bubbling reel-settle event instead of polling position - it fires once a card is actually at rest in focus, not on every card passed through while spinning past it. 

document.getElementById('myReel').addEventListener('reel-settle', (e) => {
  resetPreview(e.target);
});

Methods

MethodDescription
new Reel(root, options)Constructs directly against a root element carrying .reel-track (used internally by initAll, and just as valid to call yourself).
.refresh()Re-reads which cards are currently visible (skips anything hidden), remeasures the ring's radii, and jumps back to card 0 - call after changing which cards are shown.
.update(options)Merges new option values in, then remeasures and redraws - the animation loop parks itself whenever the ring is still, so a live change can't wait for the next frame that happens to run.
.step(direction, count)Spins the ring by count cards (default 1) in direction. A nudge to the settle spring, not a queued step: several in a row blend into one spin. Clamped at the two ends with loop off.
.next(count) / .prev(count).step(1, count) and .step(-1, count).
.to(index)Brings index into focus - by the shortest way round while looping, resolved against the current position so a ring spun several laps doesn't unwind them all. An index outside the ring wraps round it while looping (so .to(-1) is the last card) and stops at the nearer end when not.
.first() / .last()The two ends, by the same spin .to() makes - so on a looping ring .first() from the last card is one step forward, not a lap back.
.jump(index)Puts index in focus at once, with no spin - the cut to .to()'s travelling shot. Still lands dead on the card, so reel-settle fires and the position is persisted just as after a spin.
.play() / .pause()Start and stop the autoplay timer without touching the option. .pause() survives a later update(); .play() is what undoes it.
.playingWhether the timer is running - false after .pause(), for autoplay: 0, under reduced motion, and on a ring with fewer than two cards. It says nothing about whether a beat is currently being held back for a hovered or off-screen ring: that ring is still playing, just holding still.
.indexThe focused card's index, or -1 on an empty ring.
.lengthHow many cards are on the ring (the visible ones, as of the last refresh()).
.radiusX / .radiusYThe ring's effective radii in pixels, after fitting to the box and scaling by ringSize - what's actually being drawn, rather than what was asked for.
.destroy()Stops the animation loop, clears the autoplay timer and removes every bound listener. The element stays marked as claimed, so a later initAll() skips it rather than re-initializing it.
Reel.initAll(selector, options)Default selector '.reel:not(.is-empty)'. Constructs an instance for each matching element not already claimed.
Reel.get(elOrSelector)Static lookup for an already-initialized instance, by element or selector.
Reel.getAll(selector)Every already-initialized instance matching a selector, default the same as initAll.

Events

EventDescription
reel-settleBubbles from a card once it's actually at rest in the focus position - not fired on every card passed through while spinning. event.target is the settled card.

.is-focused is the live counterpart to that event: the mechanism puts it on whichever card is nearest the focus even mid-spin, where reel-settle waits for the ring to actually come to rest. Style it for anything that should track the front card continuously - a title fading in, a border, a shadow - and listen for the event for anything that should fire once. 

.my-reel .reel-card.is-focused { box-shadow: 7px 7px 0 rgba(0, 0, 0, 0.1); }

Notes

Position and scale follow different curves on purpose: every card except the one actually settling into focus sits at a constant distance from center - a real ring, varying only by angle - rather than spiraling inward as it shrinks toward the back. Only the single card currently transitioning into or out of focus interpolates its distance from center, linearly in index distance, reaching full ring radius after just one card-step. Scale and opacity instead follow depth = (1 - cos(theta)) / 2, a gentler falloff by angle, where theta is a card's angular distance from the focus. An earlier version drove *position* off depth too, as a single cardioid radius - it looked right in principle, but x = depth * radiusX * sin(theta) is tangent to zero right at the focus no matter how depth is shaped (sin(theta) itself vanishes linearly there), so the nearest neighbor ended up sitting almost exactly behind the focused card instead of visibly beside it. Ramping position to full radius immediately - rather than growing it out from zero the way scale does - is what keeps every other card visibly on the ring instead of hidden behind the one in front.

Index distance, not angle, is what's unbounded: while looping, _pos is a continuous real number that's never clamped - spin it as many laps as you like in either direction. Each card's actual on-screen angle comes from the shortest circular distance between its index and _pos (wrapping at the card count), then that angle is clamped to +/-180deg. Without the clamp, a dense ring - many cards, or a large cardAngle - could overshoot past the single point directly behind the focus and start doubling back the wrong way; with it, anything that far out just piles up at that one back point instead. With loop: false, distances stop wrapping entirely: a card far ahead of or behind the focus stays far away rather than reappearing round the other side, and the +/-180deg clamp is what parks it (faded out) at the back.

Wheel capture, and what gets handed back: a closed loop never runs out of ring, so there's no boundary to release wheel capture at the way Sweep's strip has one - wheelAxis is the only thing deciding what passes through to the page. Taking the vertical axis means calling preventDefault on it, which stops page scroll while the pointer is over the ring; the reason it's still the default is that a mouse wheel reports nothing but deltaY, so horizontal-only silently leaves the wheel dead for everyone not on a trackpad. Turning loop off adds Sweep's boundary release on top: at either end, a scroll that can't turn the ring any further is left completely alone.

Two-phase input, same as Sweep: while wheel or drag input is actively arriving, position tracks it directly, 1:1. The moment it goes idle, a damped-spring coast takes over - velocity decays via friction while a constant pull toward the nearest card (snapStrength) is folded in, settling exactly on a card rather than wherever input stopped.

There is deliberately no hover-follow: Sweep makes whatever card is under the pointer the settle target, and on a flat strip that reads as scrubbing. On a ring it feeds back on itself. Turning the ring is itself what slides the next card under a pointer that never moved, so re-reading "the card under the pointer" every frame hands the spring a new destination on each one, and the ring ends up chasing its own motion - racing through cards far faster than the pointer actually crossed them. It was tried here with two governors holding it down (a latch, so a new card couldn't take over mid-flight, and a cap on how far one hover could ask the ring to travel) and the honest conclusion was that a mechanism needing two governors to stop fighting the pointer doesn't belong on this one. Spinning a reel is a deliberate act: wheel, drag, click a card, or the arrow keys. The pointer merely being over the ring does exactly one thing - it pauses autoplay, so a self-turning ring holds still while someone is reading it.

Targets resolve through the shortest lap, not the raw index: a settle target is a card index plus whatever whole number of laps gets there by the shortest path from the current position - so clicking a card never sends the ring spinning several extra laps just to "arrive from the front" the way a naive target = index would once _pos had wandered far from zero. to() and click-to-select both go through it.

The loop parks when the ring is still: requestAnimationFrame only runs while something is actually moving - a drag, a scroll, or a settle spring still more than a hair from its target - and stops itself otherwise, same as Dial. That's why update() remeasures and redraws rather than leaving it to the next frame: on a parked ring there isn't one. "The spring has arrived" is deliberately the same test that finalizes the settle, rather than a second comparison alongside it: as two separate comparisons the loop could quit a hair short of the card, leaving the position at 1.0003 instead of 1 and never firing reel-settle or writing the remembered index at all.

The root is focusable, and the arrow keys spin it: unless the host already set them, tabindex="0" and role="group" go on the root element, and Left/Up/Right/Down call step() - so the ring is reachable and operable without a pointer at all. Setting either attribute yourself is respected and left alone. A key press that landed in a text field, a <select> or a contenteditable region inside a card is left entirely alone, though: a card can hold anything, and the arrow keys belong to the caret there, not to the ring.

Position is remembered per instance, per tab: same as Sweep - the focused card's index is written to sessionStorage, keyed by the root element's own id, and restored once on an instance's first refresh().

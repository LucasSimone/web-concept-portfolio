Dial

The View-Master reel itself - the cardboard disc you push into the viewer - rather than the viewer. Cards are mounted radially around a hub sitting on the bottom edge of the box, so what's in view is the top half of the reel: a fan of cards arcing over, each tilted to point outward from the center, cropped where the disc runs out of window. Twelve o'clock is the gate, and because a radially-mounted card is only upright at the top of its arc, the selected card is also the only one the right way up.

Install

<script src="dial.js"></script>

One script tag and nothing else. The disc shares its wrap-around arithmetic, its per-tab position memory and its initAll/get/getAll surface with the other three carousels here, and the file above already has that bundled in - so there is nothing extra to fetch. (Building from this repo's own source instead, that part is shared/carousel-kit.js, loaded before dial.js.) Injects its own <style> tag defining .dial, .dial-face and .dial-card plus the three parts of the reel it draws for itself - the rim, the hub and the gate mark - so no companion CSS file is required. The host supplies the box's size and the cards' own size and chrome.

Quick Start

<style>
  .my-dial { width: min(700px, 92vw); aspect-ratio: 700 / 375; }
  /* cqw = 1% of the dial's own width, so cards scale with the disc */
  .my-dial .dial-card { width: 13.7cqw; height: 18cqw; }
</style>

<div class="dial my-dial">
  <div class="dial-face">
    <div class="dial-card">One</div>
    <div class="dial-card">Two</div>
    <div class="dial-card">Three</div>
  </div>
</div>
<script src="dial.js"></script>

Auto-initializes against every .dial:not(.is-empty) element. Give the root a width and a height; roughly 2:1 suits the default half circle, since the disc is as big as min(width / 2, pivot height) allows. Size it however you like - the geometry is re-derived from the element's measured box whenever that box changes, so a fluid width is fine and is what the demo page itself uses.

Cards do not scale with the disc on their own. Their size is yours, and the disc's is derived from the box, so fixed-pixel cards on a fluid dial crowd together as it shrinks - 96px cards that clear each other by 20px at a 700px dial overlap by 56px at 360px. The fix is the cqw unit above: the component makes .dial a container-query context, so 1cqw is 1% of this dial's width (not the viewport's) and cards sized that way keep a constant share of the disc at every width. See the sizing recipe below. Only direct children of .dial-face carrying .dial-card count as cards - the rim, hub and gate are siblings of the face, not of the cards. To configure options: 

Dial.initAll('.dial', {
  cardAngle: 18,
  pivot: 0.5,
});

Recipes

How much of the disc you see

pivot is where the hub sits, as a fraction of the box height, and it's the control that most changes what the thing looks like. 1 puts the hub exactly on the bottom edge, so precisely half the reel is in view. Lift it into the box and the rest of the disc comes with it, until every card is visible and the arc closes into the reel as you'd hold it - at which point you'll want horizon raised too, or the far side fades out. 

// The whole disc in a square box
Dial.initAll('.dial', { pivot: 0.5, horizon: 180, fadeRange: 1 });

// Hub dropped below the box: a shallow slice of a much bigger reel
Dial.initAll('.dial', { pivot: 1.55, cardAngle: 15 });

Card size has to come down with the disc, though. Lifting the hub shrinks the disc to fit the box - it's only ever min(width / 2, pivot height) - so cards sized for a half circle will pile over the hub once the whole face is in view. Shrink them in CSS at the same time, the way the demo's second disc does.

Sizing the disc

By default there's nothing to set: the disc is as big as the element allows, min(width / 2, pivot height), so sizing the .dial box in CSS is all it takes and the whole thing stays responsive for free. That's the route to reach for first. 

.my-dial { width: min(700px, 92vw); aspect-ratio: 700 / 375; }

radius takes over when you want the number itself - a dial smaller than the space it's given, or one deliberately bigger than its own window. It may exceed the box's width, and that's the useful direction: the sides crop and you get a shallow slice of something large. It is clamped to the hub's height, though, because a disc taller than that would carry the gate off the top of the box and leave the selected card invisible - so going properly big means pushing pivot down to make the room, which raises the ceiling with it. Read .radius back for what's actually being drawn. 

// A small dial in a generous box
Dial.initAll('.dial', { radius: 220 });

// A wide, shallow slice of a big disc: hub pushed well below the box
Dial.initAll('.dial', { radius: 900, pivot: 2.4, cardAngle: 12 });

Whichever route you take, cards don't come along for the ride by themselves. The disc's radius is derived from the box but a card's size is plain CSS, so the two drift apart as the box changes: cards take up a larger and larger share of a shrinking disc until they crowd together and pile over the hub. The component makes .dial a container-query context precisely so there's a unit that follows this element - 1cqw is 1% of the dial's own width, not the viewport's, which matters whenever the dial isn't full-bleed. 

/* Cards hold a constant share of the disc at any width */
.my-dial { width: min(700px, 92vw); aspect-ratio: 700 / 375; }
.my-dial .dial-card { width: 13.7cqw; height: 18cqw; }

/* Text inside them wants a floor, or it vanishes on a small dial */
.my-dial .dial-card h3 { font-size: clamp(9px, 1.7cqw, 15px); }

A media query works too, but it steps rather than scales and it keys off the viewport rather than the element, so a dial in a narrow column gets the wrong answer.

One thing to pair with it: rimInset is pixels by default, and a fixed margin takes a bigger bite out of a shrinking disc, pulling the ring in faster than cqw cards shrink until neighbors that cleared each other at full size overlap. Give it a value below 1 and it's read as a fraction of the radius instead, which makes the whole layout scale-invariant - clearance then shrinks proportionally rather than running out. 

// 0.05 = 5% of the radius, at any dial size
Dial.initAll('.dial', { rimInset: 0.05 });

Which way the wheel turns it

wheelAxis decides which scroll axis the disc takes. It defaults to 'both', meaning each event goes to whichever axis dominates it, because a mouse wheel reports only a vertical delta - horizontal-only would leave the wheel dead for anyone not on a trackpad.

The trade-off is that taking the vertical axis means calling preventDefault on it, so the page stops scrolling while the pointer is over the disc. A disc is a closed loop with no end at which to hand capture back, so moving the pointer off it is the only escape. If that matters more than a working mouse wheel - a disc in the middle of a long page, say - 'horizontal' never interferes with the page at all. 

// Never touches page scrolling; trackpad only, in practice
Dial.initAll('.dial', { wheelAxis: 'horizontal' });

// Mouse wheel only, ignoring sideways trackpad drift
Dial.initAll('.dial', { wheelAxis: 'vertical' });

A real reel's geometry

A View-Master reel carries 14 frames and shows 7 at a time. cardAngle is degrees of disc per card, so 360 / 14 with 14 cards closes the disc exactly and puts seven of them above the horizon. Lower values crowd more cards into the visible arc and make each turn a smaller rotation; higher ones spread them out. 

// Fourteen frames, seven in view
Dial.initAll('.dial', { cardAngle: 360 / 14 });

// A fanned deck - cards shingled rather than spaced
Dial.initAll('.dial', { cardAngle: 11, rimInset: 16 });

Cards sit apart from each other only while the chord between neighbors clears their width - 2 * ringRadius * sin(cardAngle / 2) >= card width. Push cardAngle below that and they shingle instead, which isn't prevented: with the z-order stacking outward from the gate it reads as a fanned deck with the selected card standing proud of it, which is a perfectly good look to want.

Letting a card be content, not just a target

clickToSelect gives cards a two-stage click: a click on a card that isn't at the gate spins it up there and is swallowed, while a click on the card already at the gate passes straight through. So a card full of links behaves as "bring it to the front, then use it" with no extra control and nothing to wire up. Turn it off and every click passes through immediately, leaving drag, scroll and the arrow keys to do the turning. 

Dial.initAll('.dial', { clickToSelect: false });

Cards of different sizes on one disc

Nothing to configure - each card's distance from the hub is worked out from its own measured height, so a disc carries whatever mix you give it and every card still sits flush against the rim, taller ones simply reaching further in. A card is also just markup: a paragraph, an <img>, a video, a <figure> or <blockquote> carrying .dial-card directly - the mechanism only ever touches its transform and opacity.

The one thing to keep an eye on is width: neighbors sit apart only while the chord clears the widest of them, so a disc of big cards wants a wider cardAngle. And because the ring radius is derived from card height, anything that changes a card's height after layout (an image without dimensions, a font swap) wants a refresh() afterward. 

// 200x260 cards need roughly 44deg to clear each other
Dial.initAll('.dial', { cardAngle: 44, rimInset: 24 });

myImage.addEventListener('load', () => Dial.get('#myDial').refresh());

Styling the card at the gate

.is-selected lands on whichever card is nearest the gate and tracks the spin live, rather than waiting for it to settle - so it's the hook for anything that should follow the disc as it turns. Keep the styling to things that don't change the card's box: its height feeds the ring radius, so revealing content by adding layout would move every card on the disc. Fade it instead. 

.card__caption { opacity: 0; transition: opacity .18s ease; }
.card.is-selected .card__caption { opacity: 1; }

Reacting to the selected card

Listen for the bubbling dial-settle event when you want the card that actually came to rest at the gate rather than every card turned past on the way there - a flicked spin through nine cards fires it once, at the end. 

document.getElementById('myDial').addEventListener('dial-settle', (e) => {
  caption.textContent = e.target.dataset.title;
});

Methods

.step(direction, count)Turns the disc by count cards (default 1) in direction (default forward). A nudge to the settle spring rather than a queued step, so several in a row blend into one turn.

Notes

The angle is the whole of a card's state: every card is rigidly mounted to one disc, so theta = (i - pos) * cardAngle and position (radius * sin/cos theta), tilt, opacity and scale all read off that single number. Nothing is tracked per card. The disc's own radius isn't an option either - it's whatever fits the box, min(width / 2, pivot height) - and each card's own ring radius is derived from that and from its own height, so its outer edge always lands rimInset short of the rim whatever size it is. That per-card derivation is what lets one disc carry mismatched cards: a shared ring measured off a single card would seat that one and leave every other floating short of the rim or hanging over it. The radius is taken at the card's selected size rather than its resting one, so a card growing into the gate never eats the margin or runs over the index mark sitting in it.

Drag is rotational, which is the real departure: Sweep, Reel and Deck all read a linear drag - pixels across, converted to cards. A disc doesn't work that way. Grabbing it anywhere and moving the pointer turns it by the angle swept around the hub, 1:1, so the card under your finger stays under your finger wherever on the face you grabbed it. Releasing hands the remaining angular velocity to the same damped spring Sweep and Reel coast on, which always settles exactly on a card.

Angles are accumulated, not measured from the press: taking the angle since pointerdown would be simpler, but it breaks the moment the pointer crosses the hub, where the angle is undefined and flips by 180 degrees - the disc would snap a half turn. Deltas are instead summed per pointer-move and any single move that appears to sweep more than 90 degrees is discarded as a jump across the center rather than believed. A press that starts inside the hub's dead zone doesn't begin a turn at all, for the same reason.

Two clicks, two meanings: a click on a card away from the gate is a navigation request and is swallowed; a click on the card already at the gate is left completely alone, so its own links and buttons behave normally. That's what lets cards hold real content without a separate "open" affordance. Reel's clickToSelect works exactly the same way, for the same reason; Deck is the one that differs, because a frame fills the whole box and there is no "other card" to click.

The root is focusable, and the arrow keys turn it: unless the host already set them, tabindex="0" and role="group" go on the root element, and Left/Up/Right/Down call step(), so the disc is reachable and operable without a pointer at all. A key press that landed in a text field, a <select> or a contenteditable region inside a card is left entirely alone, though: a card can hold anything, and the arrow keys belong to the caret there, not to the disc.

The wheel takes both axes: the same control, the same default and the same trade-off as Reel's. Sweep accepts only a horizontal-dominant scroll, and Deck's wheel: 'x' does the same by default, so that page scrolling is never interrupted. The reasoning is sound and the consequence is not: a mouse wheel reports nothing but deltaY, so horizontal-only leaves the wheel simply dead for anyone not on a trackpad. Dial assigns each event to whichever axis dominates it and lets wheelAxis decide which of those it keeps, taking both by default. Accepting the vertical axis does mean calling preventDefault on it, and a closed loop has no boundary at which to hand that back the way Sweep's strip does, so the page stops scrolling while the pointer is over the disc - moving it off is the escape. wheelAxis: 'horizontal' restores the never-interferes behavior for anyone who wants it. Down and right both read as forward, so the two axes agree about which way the disc turns.

The loop parks itself: unlike Sweep's always-on tick, the animation loop here runs only while the disc is actually turning - a live drag, arriving wheel input, or a spring that hasn't come to rest - and cancels itself the moment it settles exactly on a card. Reel parks the same way. The test for "the spring has arrived" is deliberately the same one that finalizes the settle, rather than a second comparison alongside it: two separate comparisons let the loop quit a hair short of the card, leaving the position at 1.0003 instead of 1 and never firing dial-settle at all. An IntersectionObserver still stops it off screen, same rootMargin as the rest of this category.

Position is unbounded, angles aren't: pos is a continuous real number that's never clamped - spin the disc as many turns as you like in either direction. Each card's on-screen angle comes from the shortest circular distance between its index and pos, then gets clamped to +/-180 degrees so a dense disc (many cards, or a big cardAngle) piles up at the point opposite the gate instead of doubling back round the wrong side. Same treatment as Reel's ring, for the same reason.

Position is remembered per instance, per tab: same as the rest of this category - the selected card's index is written to sessionStorage, keyed by the root element's own id, and restored once on an instance's first refresh().

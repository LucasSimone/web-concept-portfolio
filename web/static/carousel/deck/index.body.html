One engine, any transition

Deck

One box, a stack of frames in it, and a transition that decides what moving between them looks like: a slide, a crossfade, a turning cube face, a card dealt off the top, or the arc of a View-Master reel. Everything else is identical whichever you pick — click, scroll, swipe, arrows, dots, keyboard. Switch transitions in the panel.

Six built in

Same component six times, with a different data-transition in the markup. A transition maps one number — how far a frame sits from the one in view — to a transform and an opacity, so a new one is a dozen lines, not a fork. Five of the six follow a drag 1:1 and settle where you let go. The arc doesn't: a frame stopped halfway through a swing isn't a pose to rest in.

Two custom properties and one option

Or no box at all

--dk-body: transparent removes the slab behind the frames, and clip: false stops the box being a window they can't leave. A stack becomes loose cards lying on the page, with the page's own background between them. The component is unchanged — these are the same stack transition as above, minus the background, plus a shadow from this page's CSS.

Dealt onto the page

No background, no clipping — the frames are just boxes the deck happens to be positioning.

The pile is real

Each waiting card is the next frame, scaled and offset. It isn't decoration behind the top one.

Fades before it leaves

With nothing to clip it, the thrown card has to hit zero opacity exactly one frame out. That's what the transition does.

A dozen lines

Or write your own

A transition is a plain object on Deck.transitions. It gets a frame, that frame's signed distance from the one in view, and a context holding the measured box, the resolved options and the direction of travel. The deck below runs exactly this code — demo.js registers it on load, and the markup asks for it by name with data-transition="flip" like any built-in.

Deck.transitions.flip = {
  scrub: true,
  cull: 1.05,
  defaults: { flipTilt: 90 },
  measure(ctx, frames) {
    ctx.port.style.perspective = `${Math.round(ctx.w * 2)}px`;
    frames.forEach((f) => { f.style.transformOrigin = '50% 50%'; });
  },
  style(frame, delta, ctx) {
    frame.style.transform =
      `rotateX(${(-delta * ctx.options.flipTilt).toFixed(2)}deg)`
      + ` translate3d(0, ${(delta * 100).toFixed(2)}%, 0)`;
  },
};

A frame holds anything

It isn't a photo viewer

A frame is an empty box that fills the deck. Put markup in it. These hold text, a link and a stat, none of them sized directly: .deck is a container-query context, so everything inside measures in cqw and scales with the deck instead of the viewport. Only the resting frame is interactive — try tabbing to the link, then advancing.

Bring your own buttons

Drive it from your own controls

Any element on the page can drive a deck without JavaScript of your own. One delegated listener picks up data-deck-next, data-deck-prev and data-deck-to="N", scoped by the deck they sit inside or by data-deck-for="#id". The built-in arrows and dots use the same hooks; this deck has them switched off. The lever is a <span data-deck-lever> styled entirely by this page — while you pull it the component publishes --dk-pull, and that's all its CSS needs.

Two custom properties

Sizing is a ratio and a max width

A deck is width: 100% at aspect-ratio: var(--dk-aspect, 3 / 2), so it fills whatever holds it and keeps its shape at every width. Set --dk-aspect, cap it with max-width, done — an explicit height wins over both. These three are one component sized inline, in a grid that reflows on a narrow screen; the hit targets on the small ones shrink via container query.

The round one is --dk-radius: 50% with autoplay on, which pauses the moment you hover or focus it.
